# Missing EIP-712 types

| Status | Owner | Needed by |
| --- | --- | --- |
| Accepted | Shreyas, Pradnyesh | Phase 1 |

## Problem

Early versions of `docs/api.md` lacked EIP-712 typed-data definitions for session-signed read queries (`POST /balance`, `POST /intents/status`) and intent cancellations (`POST /intents/cancel`).

## Existing behavior

Both `SessionQuery` and `CancelIntent` have been implemented and unit-tested in `packages/shared/src/eip712.ts`.

## Decision

1. **`SessionQuery` typed data:**
   ```ts
   SessionQuery: [
     { name: 'owner', type: 'address' },
     { name: 'expiry', type: 'uint64' },
   ]
   ```
   Signed by the ephemeral `sessionKey` granted via `SessionGrant`. Crucially, `SessionQuery` does NOT consume the owner's wallet nonce. This allows parallel reads from the frontend without blocking or colliding with wallet-signed operations.
2. **`CancelIntent` typed data:**
   ```ts
   CancelIntent: [
     { name: 'owner', type: 'address' },
     { name: 'intentId', type: 'bytes32' },
     { name: 'nonce', type: 'uint64' },
     { name: 'expiry', type: 'uint64' },
   ]
   ```
   Signed by the owner's primary wallet. Consumes an owner wallet nonce inside the serialized execution queue to protect against replay attacks.

## Alternatives considered

- **Reusing `DepositRequest` or omitting typed messages for reads:** Rejected because typed structured data ensures integrity, prevents URL/path tampering, and enforces strict expiry checks.

## Consequences

- Frontend can sign reads with session keys.
- Intent cancellations are authenticated, nonce-protected, and replay-proof.
